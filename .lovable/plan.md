## What's actually broken (verified in code + DB)

**1. The deliverable detail page reads the wrong account when impersonating.**
`src/routes/_authenticated/dashboard/workflow.$key.tsx` queries `attendee_deliverables` with `user_id = user.id` from `useAuth()`. Generation already targets the *effective* user (`userPipeline.functions.ts` passes `getEffectiveUserId()`), so while viewing as a founder you generate into their row and then read the admin's row — the page looks like nothing happened. Same mismatch drives the hero-image and intake queries.

**2. "Generation complete" is a lie, so the flow feels broken.**
`dashboard-pipeline-run` returns immediately and finishes the work in the background (unless `forceRun`). The UI toasts "Generation complete" the moment the request returns, then the card stays empty for a minute. `runCategory` loops over keys awaiting those same instant returns, so a whole category fires as concurrent background jobs with no progress and no ordering.

**3. Category / section-by-section running has no state.**
There's a single global "Run remaining" bar. Per-category runs show only a local spinner, per-item runs show nothing, and there's no way to cancel, retry a single failure, or see which key is being written. That's the "lost fluid continuity" — the run's own `ai_pipeline_runs` row already has the data; the UI just doesn't map it back to cards.

**4. A real crash in admin runs.** `adminRunForUser` in `userPipeline.functions.ts` reads a variable `forceRun` that was never destructured — the function throws `ReferenceError` before it ever calls the edge function.

**5. The Website PRD is being generated by the generic deliverable prompt.**
`deliverable_types.website_prd` runs through `dashboard-pipeline-run`'s one-size-fits-all system prompt: *"Aim for 3-6 sections, 100-220 words each."* That caps the PRD at roughly 1,200 words regardless of how much corpus exists — which is exactly why it stopped producing the deep PRDs. It also has `depends_on_keys = []`, so it ignores brand kit, offer, and positioning assets, and gets one 10-chunk corpus retrieval for the whole document.

## The plan

### Phase 1 — Make the workflow honest and impersonation-safe
- Replace `user.id` with the effective user id in `workflow.$key.tsx` (deliverable, intake, hero-image queries) and include it in every React Query key so switching accounts can't serve cached data.
- Fix the `adminRunForUser` `forceRun` bug.
- Sweep the remaining dashboard workflow fetchers for the same `useAuth().user.id` pattern and route them through `getEffectiveUserId()`.

### Phase 2 — Restore continuity: run all, run a category, run one
- Have `dashboard-pipeline-run` accept `keys: string[]` (an ordered subset) so a category is one server-side run in dependency order instead of N racing invocations.
- Return the `runId` for every trigger and track it client-side: subscribe to `ai_pipeline_runs` + `ai_pipeline_steps` so each card shows *queued → writing → done/failed* with the actual key in flight.
- Replace the instant "Generation complete" toast with live status; success fires when the run row completes.
- Per-card and per-category controls: Generate, Regenerate, Retry failed only, and Redirect (the existing rewrite-feedback dialog) available at the card level, not just inside the detail page.
- Keep one global "Run remaining" with its progress bar, but derive its numbers from run rows rather than a client snapshot, so a refresh doesn't lose the progress bar.

### Phase 3 — A real Website PRD generator
- Add a per-type prompt profile so long-form documents escape the 3-6 section cap. `website_prd` gets its own profile: 10-16 sections, 400-900 words each, with a fixed spine — Product summary · ICP & jobs-to-be-done · Positioning and message hierarchy · Information architecture / sitemap · Page-by-page specs (hero, sections, copy blocks, CTAs) · Brand & design tokens · Content inventory · SEO & metadata · Analytics & conversion events · Tech/data notes · Launch checklist · **Appendix: paste-ready AI-builder prompt**.
- Multi-pass generation (outline → section batches → assembly) so length isn't bounded by one completion, matching how the good TAP PRD was produced.
- Multi-query corpus retrieval: instead of one 10-chunk lookup, retrieve per section topic (brand, offer, audience, proof, product) and dedupe — the PRD then actually reflects the founder's uploaded material.
- Set `depends_on_keys` for `website_prd` to the brand/offer/positioning assets so it inherits already-generated decisions, and keep it on the pro model.
- A grounding check: log corpus chars per section batch and fail loudly (visible in the run row) if retrieval returned nothing, instead of silently writing a generic PRD.

### Phase 4 — Verify end to end
- Run one full pass as a founder and one while impersonating, and confirm from the database that content lands on the founder's `user_id`, the run row completes, and the PRD contains corpus-only facts.
