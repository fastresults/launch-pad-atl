# AI checkpoint summaries between brief blocks + persistent founder memory

## Goal

Two connected upgrades to the brief wizard (`/dashboard/brief`):

1. **Checkpoint summaries.** Break the 10 brief questions into thematic blocks. After each block, show an AI-written summary of what the founder just said, so they feel heard and can confirm or fix it before moving on.
2. **Persistent founder memory.** Save every block's questions, raw answers, voice transcripts, and the AI summary into a durable "founder memory" store. The downstream AI pipeline (the 25 workshop-day deliverables) reads from this store, so the founder's own words and the AI's understanding of them carry forward into every deliverable.

## Block layout

Group the existing 10 `BRIEF_FIELDS` (no schema change to `attendee_business_brief`) into 3 blocks:

1. **Your story** (Q1–3): `one_line_pitch`, `origin_story`, `problem_statement`
2. **Your customer & edge** (Q4–6): `target_customer`, `unique_insight`, `offer_description`
3. **Your model & vision** (Q7–10): `pricing_idea`, `business_model`, `inspiration_brands`, `twelve_month_vision`

After Q3, Q6, and Q10 the wizard pauses on a **Checkpoint screen** instead of advancing straight to the next question.

## Checkpoint screen UX

A full-width card inside the wizard layout:

- Eyebrow: `Checkpoint · Block 1 of 3`
- Heading: e.g. "Here's what we heard about your story."
- Body: 3–5 sentence AI summary + 3–4 short bullets of key takeaways (one per question in the block).
- Small "Generated by your AI assistant" line.
- Loading skeleton while generating.
- Buttons:
  - Primary: `Sounds right — keep going` → advances to first question of next block (or `/dashboard` after the final block).
  - Secondary: `Edit my answers` → returns to the first question of the block just completed.
- If the AI call fails: friendly inline message ("We couldn't generate a recap, but your answers are saved.") and keep both buttons.

## Founder memory store (new)

New table `public.attendee_founder_memory` (one row per user per memory entry). Captures one immutable "memory" per checkpoint, plus room for other kinds of memory we may add later (e.g. workshop-day stage summaries).

Columns:
- `id` uuid pk
- `user_id` uuid not null
- `source` text not null — e.g. `'brief_block'` (future-proof for `'stage_intake'`, `'voice_note'`, etc.)
- `source_key` text not null — e.g. `'block_1'`, `'block_2'`, `'block_3'`
- `block_n` int — 1/2/3 for brief blocks; null for other sources
- `field_keys` text[] not null — the brief field keys included in this memory
- `qa` jsonb not null — `[{ key, label, answer, voice_transcript }]` for each question in the block, captured at the moment of summarization
- `summary` text — the AI's prose summary
- `bullets` text[] — the AI's extracted key takeaways
- `model` text — model used (e.g. `google/gemini-3-flash-preview`)
- `content_hash` text — stable hash of the answers, so we can detect when answers changed and re-summarize
- `superseded_at` timestamptz — set when a newer memory for the same `(user_id, source, source_key)` is written
- `created_at` / `updated_at` timestamps

Indexes: `(user_id, source, source_key, superseded_at)`, `(user_id, source, created_at desc)`.

RLS (mirrors `attendee_business_brief`):
- Users read/insert/update their own rows; admins read all.
- No client deletes; service role only.
- Standard GRANTs to `authenticated` and `service_role` (no anon).

Behavior on revisit:
- If the founder lands on a checkpoint and a current (non-superseded) memory exists with the same `content_hash`, show that cached memory immediately.
- If answers changed (different `content_hash`) or no memory exists, generate a fresh one, mark the prior memory `superseded_at = now()`, and insert the new one.

## Data + AI

New server function `summarizeBriefBlock` in `src/lib/brief.functions.ts`:

- Auth-protected via `requireSupabaseAuth` (same pattern as `updateBriefField`).
- Input (Zod): `{ block: 1 | 2 | 3 }`.
- Loads the user's brief row, picks the fields + voice transcripts for that block, computes `content_hash`.
- If a non-superseded memory exists with that hash, returns it as-is.
- Otherwise calls **Lovable AI** through the existing `createLovableAiGatewayProvider` helper in `src/lib/ai-gateway.server.ts` using `google/gemini-3-flash-preview` and `generateText` + `Output.object` for `{ summary: string; bullets: string[] }`. 3–5 sentence summary, 3–4 short bullets, second person, no fabricated facts.
- System prompt enforces the "startup" wording (per project memory: never "business" in user-facing copy).
- Persists the new row in `attendee_founder_memory`, marks any prior memory for the same `(user_id, 'brief_block', 'block_N')` as `superseded_at = now()`, returns the structured object.

New server function `getFounderMemory` in `src/lib/founderMemory.functions.ts`:

- Auth-protected, returns all current (non-superseded) memory rows for the calling user, ordered by source/source_key.
- Used by both the wizard (to short-circuit when a fresh memory exists) and the AI pipeline.

## Wiring founder memory into the 25-deliverable pipeline

The AI pipeline that generates the 25 workshop-day deliverables already runs from `src/lib/pipeline.functions.ts` against `ai_pipeline_runs` / `ai_pipeline_steps`. Extend it so every step prompt includes a compact "Founder memory" context block:

- New helper `loadFounderContext(supabase, userId)` in `src/lib/founderMemory.server.ts`:
  - Loads the brief row.
  - Loads all current `attendee_founder_memory` rows for the user.
  - Returns a single Markdown string: founder's raw answers, then each block's AI summary + bullets, clearly labeled.
- The pipeline runner prepends this context to each deliverable's prompt (under a `## Founder memory` section) before sending to the model.
- Snapshot the same string into `ai_pipeline_steps.input_snapshot.founder_context` so we can audit what the AI saw for each run.

This means: as the founder completes blocks, every checkpoint summary becomes durable context the 25 deliverables can rely on — not just the raw answers.

## Wizard changes (`src/routes/_authenticated/dashboard.brief.tsx`)

- Add a `BLOCKS` constant derived from `BRIEF_FIELDS`.
- Track new state: `mode: "question" | "checkpoint"` and `checkpointBlock: 1|2|3 | null`.
- When `goNext` is called on the last question of a block, save the answer, then switch to `mode: "checkpoint"` instead of incrementing `idx`.
- Render `<BlockCheckpoint block={n} fieldKeys={…} />` when in checkpoint mode; otherwise render today's question view.
- "Sounds right" → advance `idx` to first question of next block, or finalize and navigate to `/dashboard` after block 3 (preserving the existing success toast).
- "Edit my answers" → set `idx` back to the block's first question, switch `mode` to `"question"`.
- Update the progress bar so checkpoints count as their own steps (10 questions + 3 checkpoints = 13). Update the eyebrow to handle "Checkpoint X of 3".
- Skip-to-question grid stays as-is.
